# ERC721 / ERC1155 Audit Reference

Load when the contract implements or interacts with NFTs (ERC721, ERC1155). NFT bugs differ from fungible-token bugs because of the per-id state, the `safeTransferFrom` callback, and the typical mint/reveal mechanics.

## Reentrancy via `onERC721Received` / `onERC1155Received`

`safeTransferFrom` calls `onERC721Received` on the recipient if it's a contract. This is the most common reentrancy vector in NFT protocols.

**Audit checks:**
- Are NFT transfers in CEI order? Update internal accounting before the safeTransfer.
- Is reentrancy possible into mint/buy/claim functions during a recipient callback?
- Does the contract use `_mint` (no callback) or `_safeMint` (callback) consistently?
- For ERC1155 batch operations, the callback fires after the entire batch — but balance changes happen as the batch executes.

## Mint mechanics

### Per-address mint limits
Easy to bypass via multiple EOAs. If the goal is fairness, per-address is insufficient.

**Audit checks:**
- Is the limit enforced based on EOA, contract caller, or merkle proof? Each has different bypass paths.
- Can a contract loop and mint repeatedly within a single tx?
- Is there a tx.origin check (problematic for legitimate smart wallet users)?

### Whitelist mints (merkle proof)
Common pattern: leaves are addresses (and optional max amount), proof is checked against root.

**Audit checks:**
- Is the leaf hashed with `keccak256(abi.encodePacked(address, amount))` — collision risk if amount is dynamic-sized?
- Are proofs reusable (no nonce/used flag)?
- Is the tree commitment immutable, or can the admin change it post-launch?
- Are leaves leaked publicly before mint opens (front-runnable)?

### Public mint with predictable randomness
Reveal mechanisms based on `block.timestamp`, `blockhash(block.number-1)`, or pre-image of next-block hash are exploitable.

**Audit checks:**
- Is randomness from Chainlink VRF, commit-reveal, or another secure source?
- Can a minter abort (revert) if their would-be ID is bad? (Sandbagging via `try/catch`.)
- Is the reveal time bound — can the operator delay reveal indefinitely to manipulate?

### Bonding curve mints
Price increases per mint. Sandwich-able.

**Audit checks:**
- Is the curve resistant to manipulation by the deployer (pre-mint, then dump)?
- Slippage protection: does the mint take a `maxPrice` parameter?

## Royalties (ERC2981)

EIP-2981 is informational; marketplaces may or may not honor royalties.

**Audit checks:**
- Does the protocol assume royalties are paid? Many marketplaces (Blur, OpenSea optional) skip them.
- Royalty receiver: hardcoded, owner-settable, per-token? Each has different attack surface.

## Approval mechanics

`approve(addr, tokenId)` is per-token. `setApprovalForAll(addr, true)` is for all tokens of the user.

**Audit checks:**
- Is `setApprovalForAll` revoked when expected (after a sale, transfer)?
- Can a malicious contract trick a user into setApprovalForAll via a misleading frontend?
- Does the protocol clear approvals on transfer (it should, automatically via ERC721).

## ERC1155-specific: batch operations

`safeBatchTransferFrom` transfers multiple ids/amounts atomically.

**Audit checks:**
- During a batch, balances update progressively. Are intermediate states observable by reentrant callbacks?
- Are zero-amount or zero-id entries handled gracefully?
- Is the array length bounded to prevent gas-DoS?

## Metadata manipulation

`tokenURI(tokenId)` returns metadata. Often points to IPFS or a centralized server.

**Audit checks:**
- Is metadata mutable (centralized URL → owner can rug post-mint)?
- IPFS pinning: who pays for it long-term? (Protocol risk, not security per se.)
- Is base URI changeable? By whom?

## Soulbound / non-transferable patterns

Some NFTs override `_transfer` to revert. If the override is incomplete, transferability leaks.

**Audit checks:**
- Are all transfer paths blocked: `transferFrom`, `safeTransferFrom` (both overloads), `_transfer`, `_safeTransfer`?
- For ERC1155, is `safeBatchTransferFrom` also blocked?
- Are approvals also blocked (or are they silently allowed but ineffective)?

## Token ID generation

If IDs are user-controllable, conflicts and squatting attacks are possible.

**Audit checks:**
- Are IDs sequential (`_nextId++`) or hash-derived?
- For hash-derived IDs (deed-style), can the user choose the input to force collisions or pre-mint?

## Lending / staking against NFTs

NFT-backed lending has unique challenges: floor-price oracles, illiquid collateral.

**Audit checks:**
- Floor-price oracle: from where? OpenSea API is centralized; on-chain TWAP from NFT AMMs (Sudoswap, Reservoir) has thin liquidity.
- Wash-trading the floor to inflate borrow capacity.
- Staking NFTs: rewards based on rarity/traits — is the rarity calculation manipulable or admin-set?

## Specific past exploits

- **Akutar mint (2022)**: refund logic with `transfer` instead of `call`, locked $34M.
- **OpenSea hack (multiple)**: stale signed listings.
- **Larva Labs Meebits**: predictable randomness in `randomIndex`, attacker minted rare ones repeatedly.
