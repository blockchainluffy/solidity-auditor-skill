# ERC4626 Audit Reference

Load when the contract implements or extends ERC4626 (tokenized vaults). The standard is widely adopted but has many sharp edges that have caused real exploits (Cream, several Yearn-likes, multiple lending protocols).

## The inflation attack (first depositor)

The classic ERC4626 attack. First depositor receives 1 share for some assets, then donates assets directly to the vault, inflating share price. Subsequent small deposits round to 0 shares — attacker keeps the donated value.

**Audit checks:**
- Are virtual shares / virtual assets used (OpenZeppelin's mitigation)?
- Is there a minimum-shares / minimum-deposit requirement?
- Is there a "dead shares" pattern (mint to address(0) at initialization)?
- Does the deployer pre-seed liquidity?
- Verify via test: can a 1-wei deposit by the first depositor + a 1e18 donation cause subsequent depositors to lose value to rounding?

## Rounding direction (must be in vault's favor)

ERC4626 has 4 conversion functions: `convertToShares`, `convertToAssets`, `previewDeposit`, `previewWithdraw`. The standard requires specific rounding:

- `previewDeposit` rounds down (vault favored — depositor gets fewer shares)
- `previewMint` rounds up (vault favored — depositor pays more assets)
- `previewWithdraw` rounds up (vault favored — withdrawer pays more shares for given assets)
- `previewRedeem` rounds down (vault favored — withdrawer gets fewer assets)

**Audit checks:**
- Does the implementation match these directions?
- Are all four functions consistent with each other (no arbitrage between them)?
- Is `Math.mulDiv(..., Rounding.Up/Down)` used consistently?

## Deposit/withdraw vs mint/redeem asymmetry

`deposit(assets)` and `mint(shares)` should produce equivalent results. `withdraw(assets)` and `redeem(shares)` likewise.

**Audit checks:**
- Is there any path where `deposit(X)` then `redeem(s)` doesn't return ≈ X assets, beyond expected rounding?
- Are slippage parameters present on user-facing deposit/withdraw, or is the user at the mercy of price changes during the tx?

## Asset/share confusion

Mistaking `assets` for `shares` (or vice versa) in a function parameter is a common bug.

**Audit checks:**
- Read every function that takes a `uint256 amount` — is it shares or assets? Is it labeled? Is the labeling consistent?
- In hooks (`beforeWithdraw`, `afterDeposit`, etc.), is the parameter what the function name implies?

## Hooks and inheritance pitfalls

Many ERC4626 implementations use OpenZeppelin or Solmate. Each has different hook patterns.

**Audit checks:**
- Solmate uses `beforeWithdraw(assets, shares)` and `afterDeposit(assets, shares)` — both passed.
- OZ uses `_deposit` / `_withdraw` internals — override carefully to maintain invariants.
- If the vault deploys collateral elsewhere (a strategy), the hooks must reconcile balance with the strategy. Stale balance in hooks → wrong share price.

## Re-entrancy across hooks

Vaults often interact with strategies, lending markets, or AMMs during deposit/withdraw. These external calls can re-enter the vault's deposit/withdraw functions.

**Audit checks:**
- ReentrancyGuard on all four entry points (deposit, mint, withdraw, redeem)?
- If the underlying asset is a hook-supporting token (ERC777), is reentrancy prevented?

## Total assets calculation

`totalAssets()` is used for share/asset conversion. If it can be manipulated or returns stale data, share price is wrong.

**Audit checks:**
- Does `totalAssets()` include only protocol-controlled assets, or does it use `balanceOf(this)` (donation-attackable)?
- If assets are deployed in strategies, does `totalAssets()` correctly query the strategy's current value?
- Can `totalAssets()` be temporarily inflated/deflated during a strategy operation, allowing JIT deposits to extract value?
- Slippage on strategy operations — can a malicious actor make `totalAssets()` show a fake high value?

## maxDeposit / maxMint / maxWithdraw / maxRedeem

These return the maximum the user can do, considering protocol limits.

**Audit checks:**
- If the vault has a deposit cap, does `maxDeposit` correctly reflect (cap - currentTotalAssets)?
- If withdraws are queued or limited by liquidity, does `maxWithdraw` reflect what's actually withdrawable now?
- Returning incorrect max values breaks integrators who rely on them for safety.

## Frozen vault and migration deadlocks

Protocols that integrate an ERC4626 vault often assume that `balanceOf(owner) > 0` or `convertToAssets(shares) > 0` means assets are available. That is not enough. A vault can be honest but paused, frozen, insolvent, rate-limited, or otherwise unable to satisfy withdrawals. In that state, `maxWithdraw(owner)` can return `0`, `withdraw()` can revert, or async withdrawal queues can stop progressing.

**Required test vector:**
Assume the integrated vault is frozen while the protocol still has shares:
- `vault.balanceOf(protocol) > 0`
- `vault.convertToAssets(shares) > 0`
- `vault.maxWithdraw(protocol) == 0` or `vault.withdraw(...)` reverts

Then answer:
- Do user exits/refunds/withdrawals fail?
- Can governance switch to a healthy vault while shares remain in the frozen vault?
- Does the migration path require redeeming/withdrawing old vault shares first?
- Can the protocol stop new deposits into the frozen vault without blocking refunds from liquid reserves?
- Does accounting distinguish nominal deployed assets from currently withdrawable assets?

**Common vulnerable pattern:**
```solidity
// Migration blocked while old vault shares remain.
if (oldVault.balanceOf(address(this)) != 0) revert ActivePosition();

// User exits blocked when the old vault is frozen.
if (oldVault.maxWithdraw(address(this)) < shortfall) revert InsufficientLiquidity();
oldVault.withdraw(shortfall, address(this), address(this));
```

If both patterns exist and there is no emergency override or impairment flow, add a candidate liveness finding. This is often High severity when the deadlock can permanently block all user withdrawals/refunds until the external vault recovers.

**Mitigation patterns:**
- Allow governance/timelock to mark a vault impaired and switch future deposits to a new vault without requiring zero old shares.
- Keep the impaired vault position quarantined in accounting instead of treating it as withdrawable liquidity.
- Let refunds/withdrawals continue from liquid reserves and disable auto-deposits while impaired.
- Add an explicit loss-socialization or haircut path if the protocol design allows losses.
- Emit events for impairment, migration, and recovery actions.

## Reward tokens / yield distribution

Many vaults earn rewards (CRV, COMP) that need to be sold and re-deposited.

**Audit checks:**
- Is the reward harvest function permissionless (frontrunnable to deposit just before)?
- Are rewards added to `totalAssets()` immediately, gradually (vesting), or on harvest only?
- Immediate addition lets sandwich attacks: deposit → harvest → withdraw with profit.

## Withdrawal queue / async withdrawals (ERC7540)

Some "ERC4626" vaults are actually async (deposits/withdraws take effect later).

**Audit checks:**
- If async, the vault is not standard ERC4626 — clearly document
- Pending withdrawals: who bears the loss if the vault loses value while a withdrawal is pending?
- Can pending withdrawals be cancelled? Front-run cancellations?

## Specific past exploits to check against

- **Cream Finance (2021)**: ERC4626-like inflation via direct token transfer.
- **First-depositor donation attacks** on multiple Yearn forks.
- **Hundred Finance (2023)**: rounding manipulation via empty-market exploit.
- **Curve veCRV stablecoin redemption**: share price manipulation via swap.
